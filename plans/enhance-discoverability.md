Keep public headers under include/<component>/, significant behaviour examples under features/, tests under tests/, and unfinished component work under plans/. Create these directories only when needed. Apply the same contract-location convention to a substantial nested port or subcomponent. Keep root plans/ for genuinely cross-cutting work.

Link to the existing C++ and Bazel guidance instead of repeating it. The guide should be suitable for another C++/Bazel repository using this layout.

5. Add concise writing guidance. In the reusable engineering guidance, add a short documentation section aligned with [ISO 24495-1:2023](https://www.iso.org/standard/78907.html): write for the reader’s task; make needed information relevant, findable, understandable, and usable. Use descriptive headings, direct language, concrete examples, and defined terms where needed. Apply [Diátaxis](https://diataxis.fr/start-here/) pragmatically: choose tutorial, how-to, reference, or explanation according to the reader’s need. A component README is primarily a contract/reference with enough orientation to use it; do not create all four document types by default. Do not claim formal ISO conformance.
6. Make the placement convention hard to forget. Add a small verification rule requiring a README.md for each top-level public library component identified by a BUILD.bazel and include/ directory. Use filesystem convention rather than a maintained list or Bazel parser. Add focused tests for the rule and run it through the existing verification entry point. Check presence only; do not attempt to score prose quality.

Run the repository’s verification and relevant Bazel checks. Report what moved, how someone adds and finds a new component, which checks passed, and any unresolved contract decisions. Keep the change focused; do not add a documentation generator, a Gherkin runner, or a metadata registry.
